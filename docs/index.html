待っているあいだに、別のリクエストを進める

4種類の小さな Web サーバに同じリクエストを送りました。サーバの内側（埋め込んだ計測点）と外側（10ms ごとの /proc）の両方から記録しています。どのパネルも同じ時間軸で、ドラッグすると µs の世界まで拡大できます。

      読みどころ

        数値で比べる

        CPU 時間と CPU に載った回数は、サンプラーが読んだ /proc/<pid>/task/*/schedstat の増分です（最後の 10ms ぶんは取りこぼすことがあります）。応答時間はクライアントの connect() から応答を読み終えるまで。

        観察の設計：何を、どの間隔で、どう見せるか

        同時処理の仕組みは「待ち時間のあいだに何が起きているか」に尽きます。それを見るために、性質の違う3つの記録を同じ時計（CLOCK_MONOTONIC、ナノ秒）でそろえました。

        記録取り方間隔見えるもの
        サーバの内部イベントサーバに計測点を埋め込み、起きた瞬間の時刻とスレッド ID をメモリに積む。ファイルへの書き出しは終了時に1回だけ間隔なし（起きたときだけ）accept、read、epoll_wait から戻った瞬間、I/O 待ちの開始と終了、CPU 計算、応答の送信
        クライアントのイベント同じ時計で connect → connected → sent → first → done を記録。X-Req ヘッダでサーバ側の記録と結びつける間隔なし使う人から見た待ち時間。サーバが accept する前に、カーネルの中で待たされた時間
        外からのサンプリング別プロセスが /proc を読む（サーバには手を入れない）10msスレッドの数と状態、CPU 時間（ns）、メモリ、fd の数、accept 待ちのキュー、接続数

        なぜ一定間隔のサンプリングだけでは足りないか

        イベントループが接続を受け付けてリクエストを読むまでは、数 µs〜数十 µs で終わります。10ms 間隔で覗いても、ほぼ確実にその瞬間は写りません（前回の 50ms 版で epoll の書き込み監視が写らなかったのはこのためです）。「状態」は間隔を決めて覗き、「出来事」は起きた瞬間に記録する。この2つを分けて考えるのが、設計の出発点です。

        サンプリング間隔を 10ms にした理由

        • 見たい現象の長さ：I/O 待ちは 1000ms、CPU 計算は 300ms、軽いリクエストは 50ms 刻みで届きます。10ms なら、最も短い 50ms の変化にも5点が入ります。
        • 1回の観察にかかる時間：実測で約 0.6ms です（スレッド数本の場合）。1ms 間隔にすると、500 スレッドのときは観察が追いつきません。
        • CPU 時間の精度は別に確保する：/proc/<pid>/stat の CPU 時間は 10ms 単位（CLK_TCK = 100）なので、ナノ秒単位の schedstat を読みます。間隔を細かくしなくても、CPU 時間は正確に積み上がります。
        • スレッド1本ずつの状態は、64本以下のときだけ：各スレッドの syscall と stat を読むのは重いので、500本のときは本数と CPU 時間だけにしています。

        観察そのものが結果を乱さないか

        • イベントの記録は、ロック付きの配列に時刻とスレッド ID を積むだけです。実測で1件あたり約 90ns（cargo run --release --example trace_overhead）、1リクエストあたり6〜12件なので 1µs 前後です。event_loop が accept から I/O 待ちの登録までにかける数十 µs と比べて、数 % の上乗せです。ログを画面に出す処理（println!）は、計測中は止めています。
        • サンプラーとクライアントも同じマシン（2コア）で CPU を使います。CPU 計算のシナリオでは、壁時計で数 % 長くなることがあります。
        • tokio の内部（epoll_wait を呼ぶ場所）には計測点を入れていません。スレッドのレーンは 10ms ごとのサンプルで描いています（レーン名に「〜」が付きます）。

        見せ方

        • 同じ時間軸に縦に並べる：パネルの横幅の違いが、そのまま時間の違いになります。縦軸の目盛りも、シナリオの中ではそろえています。
        • 1行 = 1リクエスト：赤（I/O 待ち）が縦に重なっていれば「同時に処理している」、階段になっていれば「1件ずつ」です。
        • スレッドのレーン：同じ時刻に、何本のスレッドが何をしていたか。赤い行の重なりと、スレッドの本数を見比べると、①と②の違いが分かります。
        • 拡大：1秒の世界と 1µs の世界を同じ図で行き来できます。前者は「待ちが重なっている」ことを、後者は「1本のスレッドが次々に処理を進めている」ことを見せます。

        再現する

        cargo run --release --bin observe -- all   # runs/ に記録（Linux）
cargo run --release --bin report           # docs/data.js を作り直す
# docs/index.html をブラウザで開く
