# 観察の設計

「Web サーバが複数のリクエストを同時にさばく仕組み」を、目で見て納得できる形にするための計測と可視化の設計メモです。結果のページは [`docs/index.html`](index.html) です。

## 1. 何を見せたいか

同時処理の仕組みは、突き詰めると次の一文に尽きます。

> 1件のリクエストは、処理時間のほとんどを「待ち」に使っている。サーバはその待ちのあいだに別のリクエストを進める。

これを見せるには、少なくとも次の4つが観察できる必要があります。

| 見せたいこと | 必要なデータ |
|---|---|
| 複数のリクエストの「待ち」が時間的に重なっている | リクエストごとの、各段階の開始と終了の時刻 |
| 重なりを作っているのが、スレッドの数なのかイベントループなのか | スレッドごとに、いつ何をしていたか（どのシステムコールで止まっていたか） |
| 待ちのあいだ、CPU はほとんど使われていない | CPU 時間（ナノ秒の精度） |
| 方式ごとの代償（スレッド数、メモリ、切り替え回数、カーネルの待ち行列） | プロセスの資源の推移 |

## 2. 記録の3つの柱

すべての記録は `CLOCK_MONOTONIC`（ナノ秒）でそろえています。同じマシン上の別プロセスでも同じ時計なので、あとから1本の時間軸に重ねられます。

### 2.1 サーバ内部のイベント（間隔なし・起きた瞬間）

サーバに計測点を埋め込みます（`src/trace.rs`）。

- 時刻・スレッド ID（OS の tid）・接続番号・種類・引数を、ロック付きの `Vec` に積むだけにする
- ファイルへの書き出しは、サーバの終了時に1回だけ（`--trace FILE --exit-after N`）
- 1件あたりの費用は実測で約 90ns（`cargo run --release --example trace_overhead`）

| kind | 意味 | 出すサーバ |
|---|---|---|
| `block` / `unblock` | スレッドが止まる呼び出しに入る／出る。arg は `accept`、`read`、`sleep`、`epoll_wait`（`unblock` では `epoll_wait:準備できた数`） | blocking、threaded、event_loop |
| `accept` | 接続を受け付けた（arg = クライアント側ポート） | 全部 |
| `request` | リクエストのヘッダを読み終えた（arg = `X-Req の番号 パス`） | 全部 |
| `wait_begin` / `wait_end` | I/O 待ち（DB 問い合わせの代わり）の開始と終了 | 全部 |
| `cpu_begin` / `cpu_end` | CPU 計算の開始と終了 | 全部 |
| `respond` | 応答を書き終えた | 全部 |
| `close` | 接続を閉じた | 全部 |
| `thread_start` / `thread_end` | 接続用スレッドの開始と終了 | threaded |

tokio の内部（epoll_wait を呼ぶ場所）には計測点を入れていません。スレッドの様子は、次の外部サンプリングで補っています。

### 2.2 クライアントのイベント（間隔なし）

`src/client.rs`。リクエストごとに1スレッドを使い、全員がそろってから一斉に開始します。

`connect` → `connected` → `sent` → `first` → `done`

各リクエストに `X-Req: <番号>` ヘッダを付け、サーバ側の `request` イベントと結びつけます。これで、「`connect()` は一瞬で返ったのに、サーバが accept したのは 4 秒後」のような、カーネルの中での待ちが見えるようになります。

### 2.3 外部からのサンプリング（10ms ごと）

`src/bin/observe.rs` のサンプラーが、サーバを子プロセスとして起動し、`/proc` を読みます。サーバ側には手を入れません。

| 値 | 読む場所 | 備考 |
|---|---|---|
| スレッド数 | `/proc/<pid>/task/` の数 | |
| CPU 時間、CPU に載った回数 | `/proc/<pid>/task/<tid>/schedstat` | ナノ秒単位。終了したスレッドは最後に見た値で合計する |
| RSS、VSZ | `/proc/<pid>/status` | |
| fd の数 | `/proc/<pid>/fd/` | |
| accept 待ちのキュー | `/proc/net/tcp` の LISTEN 行の `rx_queue` | |
| 接続数（カーネルだけ／アプリが保持） | `/proc/net/tcp` の ESTABLISHED 行の inode が 0 かどうか | |
| スレッド1本ずつの状態 | `/proc/<pid>/task/<tid>/stat`、`syscall` | 64 本以下のときだけ |

`/proc/<pid>/task/<tid>/syscall` を読むには ptrace の権限が要りますが、サンプラーはサーバを自分の子プロセスとして起動するので、通常は sudo なしで読めます。

## 3. サンプリング間隔を 10ms にした理由

1. **一瞬の出来事は、間隔をどれだけ細かくしても写らない。** イベントループが accept してから I/O 待ちを登録するまでは数 µs〜数十 µs です。これは 2.1 のイベントで記録し、サンプリングには「状態」と「量」だけを任せます。
2. **見たい現象の長さから決める。** I/O 待ちは 1000ms、CPU 計算は 300ms、軽いリクエストは 50ms 刻みで届きます。10ms 間隔なら、最も短い 50ms の変化にも5点が入ります。
3. **1回の観察の費用から上限が決まる。** 実測で、スレッド数本なら 1回 約 0.65ms、500 本なら平均 約 4ms（最大 約 33ms。スレッド数本でも、まれに 20ms 台まで延びることがあります）です。1ms 間隔では、500 本のときに観察が追いつきません。
4. **CPU 時間の精度は、間隔とは別に確保する。** `/proc/<pid>/stat` の utime / stime は 10ms 単位（CLK_TCK = 100）で、細かい比較には使えません。ナノ秒単位の `schedstat` を累積値で読めば、間隔に関係なく正確に積み上がります。
5. **重い読み取りは条件付きにする。** スレッド1本ずつの `stat` と `syscall` の読み取りは、64 本以下のときだけにしています。

前回の 50ms 版で epoll の書き込み監視（`epoll:OUT`）が写らなかったのは、1 の典型例です。

## 4. 観察が結果を乱さないか

- イベントの記録は1件約 90ns、1リクエストあたり 6〜12 件で、合計 1µs 前後です。
- 計測中は、画面へのログ出力（`println!`）を止めています（`--verbose` のときだけ出す）。
- サンプラーとクライアントも、同じマシン（記録時は 2 コア）の CPU を使います。CPU 計算のシナリオでは、壁時計で数 % 長くなることがあります。
- 500 スレッドのときは、サンプラー1回の観察が長引き、ゲージの点がまばらになります。ページにもその値を表示しています。

## 5. シナリオ

`cargo run --release --bin observe -- list` で一覧を表示できます。

| 名前 | 内容 | 何が分かるか |
|---|---|---|
| `io` | 1秒の I/O 待ちがあるリクエストを5件同時に送る | 待ちの重なり。①はスレッドの数で、②③は1本（または少数）のスレッドで重ねる |
| `cpu` | 300ms の CPU 計算を1件送り、その最中に軽いリクエストを 50ms おきに4件送る | イベントループの弱点。計算はスレッドを占有する。コア数とワーカー数の意味 |
| `scale` | 1秒の I/O 待ちを500件同時に送る（blocking は除外） | 方式ごとの代償。スレッド数、RSS と VSZ、切り替え回数、カーネルの accept 待ち |

## 6. 見せ方

- **同じ枠のまま、データだけを切り替える。** ボタン（または ← →）でサーバを切り替えても、時間軸、ゲージの縦軸、スレッドのレーンの場所は変わりません。スクロールして見比べるより、同じ位置の変化として違いが目に入ります。スレッドのレーンは、4サーバのうち一番多い本数ぶんの場所をとっておきます。縦に並べる表示（small multiples）にも切り替えられます。
- **1行 = 1リクエストのガントチャート。** 色は4つに絞りました。カーネルで待機（accept 前）、I/O 待ち、CPU 計算、その他（通信や処理）です。赤（I/O 待ち）が縦に重なっていれば同時処理、階段なら1件ずつです。
- **スレッドのレーン。** イベントがあるスレッドはイベントで正確に描き、無いスレッド（tokio）は 10ms のサンプルで描きます（レーン名に「〜」を付けます）。止まっていない時間は「CPU を使っている」として黒で塗るので、イベントループの「ほとんど青（epoll_wait）、ときどき黒い細い線」が見えます。
- **拡大。** 1秒の世界（待ちが重なる）と 1µs の世界（1本のスレッドが次々に進める）を、同じ図で行き来できます。シナリオごとに、見どころの範囲をボタンにしています。
- **ゲージ。** データの出どころ（イベントから／10ms サンプル）を見出しに書き、サンプルの値は最後のサンプルで打ち切ります。

## 7. 限界と、さらに深く見るなら

- **カーネルの中は見ていない。** 「epoll_wait がいつ起こされたか」「どのコアで動いたか」は分かりません。`perf sched timehist`、`bpftrace`（`offcputime` など）、`strace -f -tt -T` が次の一手です。
- **tokio の内部は計測していない。** タスクがどのワーカーで実行されたかは `request` イベントの tid で分かりますが、ワークスティーリングの瞬間は見えません。`tokio-console` や `tracing` の span を使うと見えます。
- **ループバックだけ。** 実ネットワークの遅延や帯域は含みません。
- **1回ずつの記録。** スレッドの生成時間など µs 単位の値は、実行ごとにばらつきます。統計的に比べるなら、各シナリオを複数回まわして分布を見るのが次の段階です。

## 8. データの形式

`runs/<シナリオ>/<サーバ>/`

| ファイル | 列 |
|---|---|
| `server_events.csv` | `ts_ns,tid,conn,kind,arg` |
| `client_events.csv` | `ts_ns,req,kind,arg` |
| `samples.csv` | `ts_ns,cost_us,threads,rss_kb,vsz_kb,fds,cpu_ns,slices,listen_q,conns_queued,conns_app,thr_running,thr_epoll,thr_futex,thr_sleep,thr_accept,thr_read,thr_other` |
| `thread_samples.csv` | `ts_ns,tid,state,syscall,run_ns` |
| `meta.json` | シナリオ、サーバ、クライアントの開始時刻、間隔、コア数、カーネル、リクエストの計画 |

`cargo run --release --bin report` を実行すると、これらを `docs/data.js` にまとめます（時刻はクライアントの開始時刻からの µs に変換されます）。
